# SM Nachrichten data model

Status: implemented; post-read visibility extension applied and verified in production on 2026-08-27.

## Scope

This domain is separate from GM Kurti chat. It supports one-way operational messages from an authenticated admin/SM-admin to one or more active Shelf Merchandisers and records delivery/read state per concrete recipient.

## Tables

### `sm_messages`

- Stable UUID primary key.
- `idempotency_key` prevents duplicate sends when the same request is retried.
- `subject` and `body` are trimmed, length-constrained and immutable after insert.
- `sender_user_id` references the creating admin account.
- `sender_name_snapshot` preserves the displayed sender at send time.
- `sent_at` is generated by the backend/database and is immutable.
- `visible_after_read_days` is an immutable delivery rule. `0` means a one-time message that leaves the SM inbox immediately after `read_at` is set. A positive value keeps it visible for that many 24-hour days after `read_at`. `NULL` is reserved for historical messages created before this rule and preserves their previous indefinitely-visible behavior.
- `is_deleted`/`deleted_at` follow the shared SM soft-delete invariant. Normal application flows cannot hard-delete or truncate rows.

### `sm_message_recipients`

- One row per `(message_id, sm_user_id)`; the database unique constraint rejects duplicates.
- `recipient_name_snapshot` and `recipient_email_snapshot` preserve who the send targeted even after later account changes.
- `delivered_at` is written with the message transaction and is immutable.
- `read_at` starts `NULL`. The only permitted business transition is `NULL` to a database-generated timestamp through the authenticated SM endpoint. Once set it cannot be modified or cleared.
- Rows have the same soft-delete/hard-delete protections as the rest of the SM domain.

## API and authorization

- `GET /admin/sm-messages`: admin/SM-admin directory, messages and recipient delivery/read state.
- `POST /admin/sm-messages`: validates unique active SM recipients and atomically inserts the message plus every recipient row. A transaction-scoped advisory lock serializes one idempotency key.
- `GET /sm/messages`: returns only recipient rows belonging to the authenticated SM and never exposes other recipients.
- `POST /sm/messages/:messageId/read`: updates only the authenticated SM's matching recipient row. It is idempotent and returns the original timestamp on retries.

Both tables have forced RLS and no direct `anon` or `authenticated` grants. The browser uses authenticated backend routes; database access remains backend-only through the service role.

## Invariants and failure behavior

- A message and all recipients commit together or not at all.
- Deactivated, deleted, non-SM or missing users cannot be recipients.
- The client cannot choose `sent_at`, `delivered_at` or `read_at`.
- One SM cannot list or mark another SM's recipient row.
- Retrying the same send idempotency key returns the original message instead of duplicating it.
- No temporary/sample message data is inserted by the migration.

## Post-read visibility contract (2026-08-27)

1. Every new admin send must choose `visibleAfterReadDays` in the range `0..3650`.
2. The admin composer exposes a clean toggle: off sends `0` (one-time); on sends an explicit day count with common presets and a bounded numeric input.
3. The rule is stored once on the immutable message row so all recipients of the same campaign have the same behavior.
4. Unread messages remain visible regardless of the configured duration.
5. The backend inbox query is authoritative. A read row is returned only while its configured visibility window is active; the browser cannot extend it.
6. The read timestamp remains immutable and database-generated.
7. Admin message history and recipient read receipts remain available after a message leaves the SM inbox.
8. Existing production messages are not rewritten or hidden by the migration; their `NULL` rule retains the old behavior.
9. “Erneut senden” creates a new immutable campaign with a new idempotency key instead of resetting recipient timestamps on the old campaign.

## Production verification — 2026-08-27

- Migration `sm_message_read_visibility` applied successfully.
- Preflight and postflight both counted one `sm_messages` row and one `sm_message_recipients` row; no row was inserted, updated or removed by the migration.
- The historical message retained `visible_after_read_days = NULL`, so its prior indefinitely-visible behavior is preserved.
- `visible_after_read_days` is nullable integer with a validated `0..3650` check; zero invalid values exist.
- The immutability trigger now rejects changes to the new delivery rule after send.
- Forced RLS remains enabled; the service role still has only `SELECT`, `INSERT` and `UPDATE` on `sm_messages`.
- Focused backend tests passed 4/4 for unread, one-time, historical and exact N × 24-hour behavior.
- Backend TypeScript and frontend production builds passed.
- Supabase advisors found no new warning caused by this column. The project-wide informational no-policy findings are expected for backend-only, forced-RLS tables; the existing leaked-password-protection warning is unrelated to SM messages.
